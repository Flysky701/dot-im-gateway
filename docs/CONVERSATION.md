# 自然回复与连续短句

普通消息读完直接回复，`reply({message_id,text})` 默认就是 final。不再要求先说“收到”，也不让用户看到 ack/final 标签。确实耗时的任务可以选择一次简短进度 ack；已选择 ack 的任务仍按原发送顺序处理，不确定发送不会盲目重发。

常驻服务默认把同一平台、同一绑定本人、同一会话的连续短文本合为一轮：最后一条之后安静 2 秒才触发事件，从第一条起最多等 8 秒。一批最多 20 条、合并正文最多 8000 字符。单条超过 1000 字符、以 `/` 开头的命令、附件消息独立处理，不等待合并。持续输入达到时间或容量上限后开启下一批，不覆盖或丢弃原消息。

`conversation: {"debounceMs":2000,"maxWaitMs":8000}` 可调整窗口；旧配置缺省时在内存采用这些值，无须重写配置。debounceMs=0 可关闭等待。临时文字入口不合并。

SQLite 保留全部原消息，另存批次成员与就绪时间。每批只生成一个稳定事件 ID。`read_message` 返回合并后的 `text`、原 `message_ids`、`batch_count` 和用于回复的根 `id`；别逐个遍历 message_ids 发回复。采集窗口未结束时直接读取/回复会返回 `batch_collecting`，稍后重试；list_pending 只列就绪批次。

事件发送前或 dot 首次读取时冻结批次。后续新消息进入下一轮，不修改 dot 已经读取的内容，也不由网关强行中断正在执行的任务。批次回复使用最新成员的 QQ msg_id 或微信 context_token，所有成员查询都指向同一回复状态。重启保留收集状态，重放入站包不会重复加入。

耗时查询中的接收到事件、事件排队等待包含这段合并窗口，不能据此判断为网络慢。dot 读取到最终回复之间还包含模型推理、工具和等待，不等于纯思考时间。

升级服务后刷新原插件工具，并给原 dot 更新旧的“先收到再结果”规则；保留已有订阅。
