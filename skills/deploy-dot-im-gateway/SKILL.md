---
name: deploy-dot-im-gateway
description: Connect a user's own QQ or Weixin private messages to their existing OpenAI dot using the self-contained dot-im-connect executable. Inspect the selected Windows/Linux target, verify a private release, guide local credential entry and owner binding, and verify a real reply. Also supports the explicitly requested legacy Linux service deployment.
---

Default to the small, one-time connection program, not a management service. Read [the portable guide](../../docs/PORTABLE.md) and [acceptance checklist](../../docs/ACCEPTANCE.md). Keep source modular; the user receives one executable for their target platform.

1. Inspect the selected target and current project processes. Do not choose a server implicitly, replace unrelated files, or reuse an active Tunnel in parallel. Prefer a verified artifact from this private repository's successful CI; match its SHA256 and commit. The executable includes Node, SQLite, the QR renderer and the official tunnel-client. No runtime npm/pip install or download is necessary. Agent-side SSH, browser and OS libraries are separate prerequisites, not bundled dependencies.
2. Run `dot-im-connect --self-test` without credentials. This checks embedded SQLite/client and temporary cleanup without contacting QQ, Weixin or OpenAI. Do not claim a real connection from this result.
3. Reuse the intended existing private Tunnel and original dot. Before any new account authorization or credential access, consolidate missing approval into one concrete scope: target machine, own text messages, selected platform, existing Tunnel runtime key with Read+Use only, process-memory credentials, temporary messages deleted at exit, and manual stop. Existing approval for this exact scope need not be repeated. The portable program does not create keys/Tunnels/plugins, persist secrets, install services, enable Events, or change firewall/SSH permissions.
4. Have the user run the executable in their own terminal and enter credentials in its loopback page. Never read or relay the key, temporary page capability URL, QR, or phone digits in tool output/chat/logs. For Linux use the user's existing strict SSH identity and an explicit loopback local forward as described in the guide; never disable host-key checking. Keep the transport terminal running. On Windows the program runs on that Windows machine, not automatically on a remote server.
5. QQ uses the user's existing official bot. The user sends the random challenge from their own QQ and confirms the observed stable ID through the separate local page. Never treat the first sender, nickname, or message claim as the owner. Do not install the upstream UNLICENSED QR helper. Weixin uses the bundled official-protocol QR flow; owner identity comes from the official confirmed response. The user scans/approves and enters any phone code themselves. Warn once that closing the program does not unlink the Weixin-side binding.
6. After the official client reports readiness, have the original dot discover exactly `gateway_status`, `list_pending`, `read_message`, `reply`; refresh the existing private plugin only if needed and authorized. Ask the user to send a text, let the original dot issue ack then final for that message ID, and verify human receipt. Do not send a local direct reply and call it original-dot acceptance. No media, subscriptions or proactive arbitrary-recipient sends are exposed by this entry.
7. The user can close the connection page after setup; the bridge and official client must keep running. Stop with Ctrl+C, verify `processes_remaining=false` and `data_removed=true`, and rerun after disconnection. No automatic re-enrollment, credential persistence, autostart or repair orchestration. On abrupt power loss/SIGKILL, cleanup cannot be guaranteed: inspect only the named temporary directory after verifying no owned process remains, without reading message/secret content.

If the user explicitly requests the older persistent Linux service, use [the deployment runbook](../../docs/DEPLOYMENT.md) and deterministic `scripts/deploy.py` plan/apply flow. Persistent credentials, service autostart and actual Events subscription each require their specific scope to be authorized. Keep callback destinations exact and signed challenge verification enabled. Do not infer these permissions from approval of a temporary connection. Preserve data on upgrade/rollback/uninstall; uncertain sends never automatically resend.
