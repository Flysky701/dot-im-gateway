# 事件回信与延迟排查

适用于现有 QQ/微信事件任务的创建和修复。沿用绑定、凭据、任务 ID 和触发器；任务说明变更不要求重新部署或扫码。

## 保存到原任务的规则

- 触发后优先取信，不先发表网页状态说明、查 gateway_status 或做时延诊断。有明确 message_id 时 read_message；缺少 ID 或同次多条时 list_pending，按顺序处理所有未完成批次，分页跟随 next_cursor。
- 当前 list_pending 已返回正文及回复状态，不为普通文字重复读取。部署版本若另有领取任务步骤，以实际工具契约为准。message_ids 是同批成员，只向根 id 回复一次；不同根 id 分别处理。已有 final、uncertain 或终态不重复执行或重发。
- 普通对话直接 reply(final)，自然回复；缺信息、附件失败或执行受阻也回原渠道。ChatGPT 网页里的回答不等于 QQ/微信回信。
- 长任务先发有意义的进度 ack，保留原平台、根 message_id 和 expires。派发时同时保留结果回传责任；拿到结果或阻塞后，窗口内用 reply(final) 回原渠道，不能只在网页报告已完成。
- 已授权的长任务结果超过回复窗口后，仅在该平台主动通知已启用且用户已授权时，用同平台 notify_owner 回传一次，固定 idempotency_key=result_<根message_id>；微信显式选择 context_mode=none。uncertain 不换 key 重发。未启用或被平台拒绝时如实报告，不能宣称已送达，不绕到另一平台。
- 同次处理完补查一次 list_pending，处理新出现的有效来信；空则结束，不定时轮询。不要用主动通知补发历史测试或重复发送已有结果。
- 单次安装检查的「不发测试消息」只约束该次管理操作，不暂停后续真实来信；用户明确暂停自动回复时必须遵守。

## 最短诊断路径

1. 先只读 gateway_status / message_timing 或服务器诊断；不要用 read_message/list_pending 充当观察工具，它们在当前版本会记录首次读取。
2. 分开比较：网关收到→事件发送、事件 HTTP 耗时、事件接受→首次取信、取信→final 入队、final→平台接受。首次取信表示工具返回消息，不代表模型已理解；取信到 final 包含工具和排队，不等于纯思考时间。
3. 事件 2xx 仅证明回调被接受。没有平台内部时间戳时，不能把「接受→取信」细分为云端调度、推理或连接耗时，也不能承诺网关能消除这段等待。
4. 已读无 final 时对照原 dot 对话和 reply 记录：没有 reply 行与发送被拒绝、uncertain 是不同故障。检查一次性禁发指令是否延续、结果是否只留在网页、同次多批是否漏处理，以及实际回复窗口。
5. 修改原任务保存的说明，重新打开确认生效与触发器保留；不只依赖聊天中的口头更新。保留历史记录，不重放过期测试。新消息由用户发起，比较同一组分段时间，再报告实际改善。
